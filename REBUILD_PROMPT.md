## What this is

A local, single-user webapp that aggregates and evidence-grades information related to *State of Utah v. Tyler James Robinson* (case 251403576) — the prosecution of the September 10, 2025 shooting of Charlie Kirk at Utah Valley University. It's a citizen-accountability tool, not a conspiracy generator: every claim is sourced, graded, and explicitly separated from verified fact.

**The one rule that governs every tab:** never present an unverified or circulating claim as established fact. Every piece of content carries a verification tier, a source, and — where a claim is contested — the counter-evidence sitting right next to it. Association is not conspiracy; the app is built to resist collapsing "these two people know each other" into "therefore involvement," and it says so explicitly wherever that temptation exists in the source material.

## Tech stack

- **Frontend**: vanilla HTML + CSS + JavaScript. No framework, no build step for the frontend itself. One `index.html`, one `app.js` (~2000+ lines, grows by appending new `load*()` functions), one `styles.css`.
- **Data layer**: static JSON files in `data/`, each generated by a Python script in `scripts/` (e.g. `build_timeline.py` → `data/timeline.json`). The Python scripts ARE the source of truth — hand-edit the `.py` file, re-run it, never hand-edit the generated JSON.
- **Server**: `python -m http.server <port>` for local serving. No Node, no npm, no database.
- **Rendering pattern**: each tab has a `<section id="tab-X">` in `index.html` and a matching `async function loadX()` in `app.js` that fetches its JSON file and builds the DOM via template-literal `innerHTML`. All `loadX()` calls fire at the bottom of `app.js` on page load; tab switching just toggles `.active` class visibility (see the `.tab-btn` click handler at the top of `app.js`) — data for every tab loads immediately, not lazily.

## Critical technical gotchas (learned the hard way — apply these from the start)

1. **Cache busting**: browsers/Python's `http.server` cache JSON responses aggressively. Every `<link>`, `<script src>`, and `fetch()` call must carry a shared version query string (`?v=N`). Bump `N` everywhere (index.html asset tags + every fetch URL in app.js) on every change that touches data or app.js, using a single find/replace across both files. A stale mismatched version between index.html and a fetch call is a common bug — after bumping, grep to confirm the new number appears in both files and the old one is gone.
2. **Gzip detection by content, not extension**: if you ingest any ADS-B/archive data where files are named `.json` but are actually gzip-compressed, detect by magic bytes (`raw[:2] == b'\x1f\x8b'`) and decompress before parsing — never trust the extension.
3. **Windows-reserved ports**: port 8765 (and some others) can be OS-reserved and fail to bind. Pick an uncommon port (this project settled on 8790) in `.claude/launch.json`.
4. **Flight-phase detection**: when deriving takeoff/landing events from a ground/airborne trace, track a `was_airborne` boolean and only fire the event on a state *transition* — naive per-point ground-checks produce false landings on every ground-to-ground point.
5. **Timestamp convention**: ADS-B trace timestamps are seconds-since-midnight-UTC. MDT = UTC−6. Always convert and always label displayed times `MDT` explicitly.

## Data pipeline pattern (apply this for every new data domain)

1. Write a `scripts/build_X.py` that defines Python dicts/lists for the content, with rich inline comments carrying source URLs and verification notes as string values (not just code comments) so they survive into the JSON.
2. Script writes `data/X.json` via `json.dumps(out, indent=2)`.
3. Add a `loadX()` function in `app.js`: `fetch("data/X.json?v=N")`, build HTML via template literals, assign to a root `<div>`'s `innerHTML`.
4. Add CSS for any new classes introduced, appended to `styles.css` (this project grew to ~900+ lines this way — one running stylesheet, not per-component files).
5. Call `loadX()` at the bottom of `app.js` alongside the other load calls.
6. Verify in-browser via the preview tool: check console for errors, spot-check rendered counts against source data (e.g. "12 entries in JSON → 12 cards in DOM").

## Evidence-grading vocabulary (reuse this exact vocabulary across tabs)

Different tabs use slightly different tiers depending on what's being graded, but they're all variations on the same idea. Define explicitly in each tab's data:

- **Evidence grade** (for circulating claims, e.g. the Trends Tracker): A = original/reproducible primary source, B = archived secondary (screenshots/transcripts), C = tertiary reposted compilation, D = unsourced.
- **Provenance** (for timeline events): `official` (court/government primary source) / `reported` (named credible reporting) / `disputed` (outlets conflict, shown as open question) / `unverified` (secondary/tertiary only).
- **Government/military connection tier** (Network tab): `service` (actually served) / `appointment` (formal advisory/oversight role) / `adjacent` (paid professional work FOR a government body, not employed by it) / `advocacy` (ideological alignment, not employment) / `none_found` / `unverified`.
- **Contested-claim rating** (Contested Claims tab): `verified` / `supported` / `documented_allegation` (the claim was definitely made; its truth is separate) / `unproven` / `counterevidence` (affirmative evidence points the other way) / `no_evidence`.
- **Person-timeline confidence** (48-Hour Window tab): `official` / `reported` / `self_reported` (the person's own claim, not independently verified) / `disputed`.

Every rating needs a `{label, color, desc}` triple defined once and reused as chips/badges throughout that tab.

## Tabs to build (11 total)

Build in roughly this order — later tabs depend on entities/events established in earlier ones.

### 1. Verified Case Map
Force-directed graph (D3-style, hand-rolled SVG physics simulation) of every named person in the case, connected to one of three hub nodes: victim, defendant, justice-system. Draggable nodes, click-to-inspect side panel showing role/verification-status/source. Data source: a flat people-roles table (`Name, Type, Case Role, Verified Summary, Case Connection Verified?, Pre-shooting Contact Found, Source URL, Name Collision Risk`) transformed into nodes+edges by inferring category from role text. No Trends/claims data drawn here — this tab is the "verified only" anchor the rest of the app can be checked against.

### 2. Assessment
A single analytical conclusion, shown with its work: framing/central-finding statement, a plain-language reconstruction paragraph, a "convergence" table (independent evidence streams that each individually have a weakness, listed honestly), a ranked list of genuine anomalies (each with severity, finding, why-it-matters, and what records would resolve it), a security-failure section, two "control case" comparisons to structurally similar historical events (with an explicit lesson: "don't dismiss anomalies, but don't promote anomalies into actors"), a confidence-range bar chart (low–high %, not point estimates, each with a caveat note), a "what would change this assessment" list paired with a "what does NOT count as evidence of X" list, an evidentiary-ladder worked example (showing how a claim can be documented → alleged → hypothesis → unproven in ascending strength, each rung labeled), and a historical-precedent comparison table. Close with a bottom-line paragraph and a "next milestone" callout (next court date + why it matters).

### 3. Court Record Timeline
Chronological event list, filterable by track (institutional / day-of / investigation / legal / evidence). Every event has date, track, title, detail, provenance tag, source URL, and a `why_listed` field explaining why it's in the record (this field is what stops the timeline from becoming an undifferentiated wall of facts). Include a `flag: "discrepancy"` field for events where sources conflict, and render those distinctly. Add an evidence-handling summary block explaining the overall pattern found (e.g., "enhancement was used but disclosed and litigated in open court, not concealed").

### 4. Official Conduct
Tracks institutional/official misconduct or evidence gaps, categorized: sanctioned (court found an actual violation) / evidence_gap / contested / transparency / unresolved. Each entry: id, title, date, actor, category, severity (1-3), what_happened, status, verification tier + note, source, what_would_resolve, optional `flag: "actionable"`. This is where you log things like an inconclusive ballistics comparison, an uncollected piece of evidence, a contempt finding, or a specific unresolved search-sequence discrepancy — always with "what would resolve it" as a mandatory field, never left as a bare accusation.

### 5. Network & Backgrounds
Person cards grouped by role (board/leadership, media/inner-circle, donors, family, security/operations), each tagged with the gov/mil tier vocabulary above, plus `finding` / `detail` / `significance` / `not_established` fields — the `not_established` field is mandatory for every person, listing exactly what was searched for and NOT found, so the reader can see the negative-result work, not just the positive hits. Below the person cards: a relationship-edges table (type-classified: employment/funding/government/advocacy/communication/family/unverified, each with a strength rating and a basis sentence), a detailed chronology block for the single most-investigatively-interesting relationship chain found (with a "key testable question" and a "records that would resolve it" list), a claim-by-claim table for any widely-circulated claim thread about a specific person (rate each individual claim, don't accept/reject the thread as a bundle), a donor-transparency note (name the structural reason a "complete donor list" can't exist — e.g. donor-advised funds), and a closing "specifically checked and NOT established" list plus a prioritized next-leads list.

### 6. Contested Claims
Deep-dive adjudication of specific circulating disputes. Each dispute: title, summary, a numbered `core_problems` list (each problem = title + body, e.g. "the date doesn't match the allegation," "the enhancement claim isn't demonstrated," "a screenshot of a livestream adds compression, it doesn't remove it"), then a full `propositions` table where EVERY individual factual sub-claim in the dispute gets its own rating from the contested-claim vocabulary above — this is the core discipline of the tab: never rate a multi-part claim as one true/false unit. Close with a bottom-line paragraph and (where relevant) a "best next step" / "what would resolve it" note.

Also build a consolidated **Contradictions** sub-section at the bottom of this tab: paired side-by-side cards (source A's claim vs. source B's claim), a why-it-matters note, a resolution status, and a pointer to the fuller entry elsewhere in the app. Compile these from every genuine A-vs-B conflict surfaced anywhere else in the app's research — internal self-contradictions by a single source count too (e.g. someone's public claim not reconciling with their own later statement).

Finally, a **methodology** section specific to whatever the noisiest recurring claim-generator is in your case (in the source project this was Google Trends spike claims) — rank the plausible explanations for the pattern from most to least likely, state the core statistical/methodological distinction being missed, and list what would actually make the strongest version of the claim credible (e.g., "original exports made BEFORE the controversy, not screenshots after" / "a control study against hundreds of unrelated names" / "subpoenaed primary records, not the public tool's cached aggregate").

### 7. External Fact-Check
Cross-references a **third-party** claims-tracking site (in the source project: an Obsidian Publish site cataloguing ~34 circulating claims with its own verdicts). Treat it explicitly as an external source to check against, not this app's own research — log its site name, URL, fetch date, and a description of its methodology up top. For each claim you pull in: id, category, title, claim text, verdict (using your own rating vocabulary, which may differ from the source site's framing), verdict_note, `for`/`against` evidence lists, sources, and — critically — an `app_cross_reference` field noting where this same ground is covered elsewhere in your own app, and explicitly flagging if the two sources disagree (disagreement is preserved, not silently resolved into a single answer).

### 8. 48-Hour Window
A per-person chronological log of movements/statements in the 48 hours before and 48 hours after the central event, built as: a `window` object (start/shooting/end timestamps + a note on time-zone convention), the confidence-legend vocabulary above, and a `people` array — each person has a role, a `coverage_note` (how well-documented their movements are and from what kind of source), and an `entries` array of `{when, event, confidence}`. This tab is for reconstructing "who was where, and how do we know" independent of the narrative interpretation layer in the Assessment tab.

### 9. Trends Claims Tracker (or equivalent circulating-claims log)
If your case has an associated body of "search-trend spike" or similar circulating pattern-claims: log every individual claim record with its evidence grade (A-D per the vocabulary above), region, claimed metric, days-before-event, and in/out-of-scope flag. Build an interactive demo panel that visually teaches WHY the underlying data source's normalization makes raw claims misleading (e.g., a slider showing how wildly different real search volumes can produce an identical-looking normalized chart) — this single demo does more to inoculate a reader against the whole claim category than any amount of prose. Include a control-group comparison panel: matched-role people who were tested the same way, to show whether the "signal" is actually specific to the people it's claimed about, or would show up for anyone.

### 10. Flight Data
Two layers:
- **Methodology layer**: explain how the underlying flight-tracking data source actually behaves (coverage gaps, what "compressed image" enhancement claims really mean, receiver density limitations) with an interactive cause-and-effect demo, plus a base-rate/registry-lookup reference block. This layer exists so a reader can evaluate any flight-related claim themselves, independent of what this app found.
- **Findings layer**: if you have access to a public historical ADS-B archive (this project used adsb.lol's historical releases, GitHub-hosted, ODbL-licensed, gzip-per-aircraft-trace, indexed by ICAO hex not geography) for your event's date — extract a target aircraft's full flight profile (SVG track colored by altitude, phase table, coverage-gap annotation), a filtered "aircraft of interest" set (foreign government/military, surveillance-type platforms, named-person/company-owned aircraft, and any timing anomaly worth flagging — arrived/departed within a tight window bracketing the event), each with owner/operator, why-flagged reasoning, and a "what would resolve it" note. Build actual per-aircraft flight-path visualizations (small-multiple SVGs, one per aircraft, altitude-colored line + ground/PVU marker + phase dots) for the full filtered set, not just a table of names — a table of names invites unfounded pattern-matching; an actual track lets the reader see whether an aircraft was truly present at the critical moment or just "in the area that day." Compute and headline the single most load-bearing stat: how many aircraft in the filtered set were actually on the ground/at-location AT the moment of the event (not "that day" — AT that moment).

**Filter discipline for the aircraft-of-interest set**: exclude piston/training aircraft and scheduled commercial/regional airline flights from a "private jet" bucket; include known military/surveillance-platform aircraft types regardless of engine class (a turboprop surveillance platform is still relevant even though it's not a "jet"); include foreign-registered government/military aircraft regardless of engine type. State these filter rules explicitly in the methodology text so a reader can audit what was excluded and why.

### 11. Sources & Methodology
Tiered source-reliability table (A/B/C definitions) plus a methodology-notes table pulled from the underlying dataset's own stated caveats. This is the "how to weigh everything you just read" reference tab.

## Content-acquisition workflow (how the source project actually built its data)

1. **Court record**: pull hearing transcripts, charging documents, named wire-service reporting. Build the verified Case Map and Court Record Timeline from this alone first — it's the spine everything else hangs off.
2. **Public archive data**: if a relevant historical dataset exists publicly (flight tracking, public records, etc.), download it, write an extraction script with the gzip/format gotchas above, and re-run targeted extractions as new named entities of interest surface — don't try to extract everything up front; extract broadly once for a filtered summary, then re-extract full detail only for the entities that end up mattering.
3. **Network/background research**: for named people around the central figures, research via web search, explicitly separating "actually served/employed by X" from "advocated for/aligned with X" — this distinction is the single highest-value discipline in the whole project. Always record negative findings (what you specifically checked and did NOT find), not just positive hits.
4. **Third-party claim trackers**: if a third-party site already catalogues circulating claims with its own verdicts, fetch and cross-reference it rather than re-litigating every claim from scratch — but always keep it in its own tab/section as an external source, never merge its verdicts silently into your own without attribution.
5. **User-supplied documents**: if the user provides a Word doc, PDF, or other file of additional research, extract its full text (including tables) before integrating — don't summarize-then-integrate, actually read the whole thing, since evidentiary nuance lives in qualifying phrases that a summary drops.
6. **Direct user claims/images**: when a user shows images or makes a specific empirical claim (e.g. "compare these two photos and tell me if it's the same person," or a claim about a private individual's identity/relationships), do NOT render a confident identity/fact verdict from casual inspection — explain the specific reliability limitations (compression generations, no shared reference scale, no chain of custody), give only what's genuinely observable without asserting a conclusion, and offer to log the claim itself (with proper sourcing) into the Contested Claims tab rather than personally adjudicating it. Decline outright to identify or profile private individuals with no public evidentiary role in the case, regardless of how the request is framed.

## Design conventions (screenshots will show you the specifics — this is just the system)

- Dark theme via CSS custom properties on `:root` (`--bg`, `--panel`, `--cork`, `--border`, `--text`, `--muted`, `--accent`, plus semantic colors `--grade-a/b/c/d` and per-category colors for map node types).
- Every tab starts with a `.panel-intro` callout stating its scope/rule in one paragraph, `.warn` variant (red left-border) when the tab's core message is a caution.
- Cards, not tables, for anything with prose content; tables for anything tabular (propositions, edges, stats).
- Small colored badge/chip components everywhere (`tier-badge`, `flag-badge`, `rating-chip`, `contra-status`) — define the color mapping once per vocabulary and reuse.
- Every numbered/prioritized list (leads, anomalies, ranked precedent) gets a small circular numbered badge, not a bare ordinal.
